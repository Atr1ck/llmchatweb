# Updream 前端岗位：Canvas Flow 项目深挖拷打文档

> 用途：针对 B 站自研 AI 视频创作平台 Updream 前端 JD，准备一轮 30–45 分钟的项目深挖。
>
> 项目定位：Canvas Flow 是一个可运行的个人 AI 图片创作画布项目。它用于证明节点画布、流式 AI、工作流调度、性能优化和工程质量能力，不应包装成真实线上生产项目。
>
> 诚实边界：当前不包含视频预览、音视频编辑时间轴、多人协同和真实线上流量。面试时主动讲清楚边界，反而比被面试官追问后暴露更可信。

---

## 0. 先背熟的项目口径

### 30 秒版本

我做了一个面向图片创作者的 AI 原生工作台 Canvas Flow。它把无限画布、素材资产、AI 对话和图片生成任务放到一个工作流里：用户可以导入参考图，在节点画布中组织图片关系，通过 SSE 流式 Agent 选择素材并触发生成，结果再回写到画布。

这个项目我重点解决了三类问题：第一是大画布的视口查询和渲染压力，用 R-tree 加 Worker 做空间索引和降级；第二是流式任务的取消、乱序和迟到事件，用任务状态机、runId 和 sequence 保护状态一致性；第三是工作流执行和工程质量，补了 DAG 校验、拓扑调度、并发限制、重试、单测、CI 和 benchmark。

它是个人可运行项目，不是线上项目，所以我会把本机 benchmark 和工程演练结果作为设计验证，不把它们说成线上收益。

### 2 分钟版本

项目由三层组成：

1. **工作台 UI**：React + TypeScript + Zustand，左侧素材栏，中间 React Flow 画布，右侧 AI 对话和 Style Bible。
2. **画布与任务层**：节点、边、资产、任务和项目记忆可以持久化到 IndexedDB；画布支持选择、拖拽、缩放、分组、撤销重做和项目切换。
3. **AI 与执行层**：后端通过 SSE 推送 Agent 状态、文本、工具调用和结果；前端处理取消、迟到事件和错误状态；工作流执行器负责 DAG 校验、拓扑依赖、最大并发、重试、失败分支传播和取消。

为了避免“为了用 Worker 而用 Worker”，我只把纯数据的空间查询放到 Worker，React、Zustand 和 React Flow 实例仍在主线程。R-tree 解决查询复杂度，Worker 解决线程阻塞，两者是互补关系。

当前验证包括：前后端 TypeScript 检查、Vitest 11 个测试、生产构建、10,000 节点/20,000 边 benchmark，以及 Worker 崩溃、流式事件迟到、DAG 重试和取消演练。

### 面试时必须主动说的边界

- 这是个人项目，不说“线上稳定运行”或“服务了多少用户”。
- 10,000 节点 benchmark 是 Node 微基准，不等于浏览器真实 FPS，也不等于线上 P95。
- 当前图片生成链路是真实接口抽象 + 本地可运行流程，未实现完整视频预览和非线性编辑时间轴。
- SSE 当前适合单向 Agent 流式输出；没有为了迎合 JD 虚构 WebSocket 多人协同经验。
- CI 和故障演练证明了工程意识，但不能替代真实线上故障处置经历；线上排障要结合正式工作项目补充。

### 结论

这个项目最适合证明：

- 你能独立拆解 AI 原生复杂前端问题；
- 你不是只会拼页面，能处理一致性、性能和取消语义；
- 你能写出可验证的技术方案并落成代码。

它不能单独证明：

- 你已经处理过真实线上高并发；
- 你做过完整视频编辑器或音视频管线；
- 你有多人协作画布、WebSocket 房间和服务端补偿经验。

## 2. 第一层：项目全局拷打

### Q1：为什么做这个项目？解决了谁的什么问题？

**推荐回答：**

传统图片生成页面通常是“输入 prompt，得到一张结果”，创作者很难管理参考图、生成关系和多轮修改。我把它设计成一个工作台：素材是有身份的资产，节点表达创作关系，右侧对话负责理解意图和调用工具，生成结果回写为新的节点。这样可以把一次创作从单次请求扩展成可观察、可回溯的工作流。

**继续拷打：**

- 用户最核心的动作是什么？
- 为什么不直接做 ChatGPT 式聊天页面？
- 画布给用户带来的具体收益是什么？
- 哪个设计是产品需求，哪个是你的技术判断？

**必须答到：**

用户需要管理“素材—提示词—生成结果—变体/融合关系”，所以画布不是装饰，而是创作上下文和结果历史的可视化容器。

### Q2：你个人到底负责了多少？

**推荐回答：**

这是我独立设计和实现的个人项目。前端核心代码包括工作台布局、React Flow 画布、Zustand 状态、IndexedDB 快照、AI 对话流式消费、资产上下文、任务状态机、Worker/R-tree 空间索引、DAG 执行器和测试门禁。后端部分实现了 Node/Express 的 Agent SSE、工具校验和 Provider 抽象，用来支撑前端链路。

**继续拷打：**

- 哪一部分最难？
- 你是否使用了第三方库？
- 如果去掉 React Flow，你能自己实现多少？
- 哪个地方是你后来重构的？为什么？

**诚实边界：**

第三方库承担基础能力，但节点数据模型、空间索引、任务状态和交互边界是自己设计的。不要说“所有能力都从零实现”。

### Q3：这个项目和 Updream 的最大相似点与最大差异是什么？

**推荐回答：**

相似点是都把 AI 对话、创作素材和节点/工作流组织到一个创作者工作台里，核心前端问题也是复杂交互、流式任务和大数据量画布。差异是当前项目聚焦图片创作，Updream 是视频创作平台，视频预览、时间轴、音轨、切片、导出和媒体资源生命周期还没有在这个项目中实现。我会把已有的任务与画布抽象复用到视频节点，再单独设计媒体时间轴，而不是把图片节点硬套成视频编辑器。

**继续拷打：**

- 如果明天让你做视频节点，第一步是什么？
- 哪些状态可以复用？哪些不能复用？
- 为什么当前阶段不先做视频？

**推荐追问答案：**

先明确视频节点协议和预览边界，再做 `<video>` 播放、加载/错误/取消和对象 URL 释放；时间轴要单独建模 `track / clip / source / range`，不能只给图片节点加一个 video URL。

## 3. 第二层：节点画布与复杂交互

### Q4：为什么选择 React Flow，而不是自己用 Canvas/SVG 实现？

**推荐回答：**

当前目标是验证创作工作台和工作流交互，React Flow 已经提供了节点/边模型、视口变换、拖拽、选择、MiniMap 和基础交互，可以把精力放在业务节点、资产关系、任务状态和性能边界上。自己用 Canvas/SVG 当然可以获得更强的绘制控制，但要重新处理命中测试、键盘操作、连线交互、可访问性和状态同步，首期成本不划算。

**继续拷打：**

- React Flow 的瓶颈在哪里？
- 10,000 个节点是否真的全部交给 React Flow？
- 节点离开视口后如何保证选中和运行状态不丢？
- 什么时候你会换成自绘 Canvas/WebGL？

**推荐答案：**

当前通过视口裁剪只把可见节点、overscan 节点、选中节点和运行中节点交给 React Flow。若节点数量继续增长，且 DOM 节点、边绘制或 React reconciliation 成为主要瓶颈，再考虑把静态缩略图层和交互层分离，使用 Canvas/WebGL 做大规模渲染，但不能只凭节点数量做迁移决定。

### Q5：节点和边的数据模型是什么？为什么要把画布层和执行层分开？

**推荐回答：**

画布层保存节点位置、尺寸、选择、分组、边和视口；执行层把节点和边解释为 DAG，负责依赖、状态、并发和重试。这样拖动节点不会影响执行语义，执行失败也不会破坏画布布局。`CanvasNode` 里保存 `assetId、prompt、sourceAssetIds、status` 等业务数据，React Flow 的实例和 Worker 只属于运行时，不进入 IndexedDB 快照。

**继续拷打：**

- 为什么不直接把 React Flow Node 存进 IndexedDB？
- `assetId` 和节点 ID 为什么要分开？
- 一个生成结果被多个节点引用时怎么处理？
- 节点协议升级后旧项目怎么办？

**推荐答案：**

资产是可复用的数据实体，节点是画布中的关系和位置，所以二者不能合并。快照只保存可序列化的领域数据；协议需要版本号和未知节点保留策略，升级时不能静默丢数据。

### Q6：复杂交互怎么保证不和输入框、画布拖动互相干扰？

**推荐回答：**

节点内部的 textarea 和 button 使用 `nodrag` 与 `stopPropagation`，避免输入行为被画布拖拽接管；画布拖动、框选、缩放和节点点击分别绑定到不同层级；快捷键先检查目标是否是 input、textarea 或 contenteditable，再处理撤销、重做、全选和删除。详情面板拖拽使用 Pointer Events 和 pointer capture，避免指针离开元素后丢失移动事件。

**继续拷打：**

- pointer capture 什么时候释放？
- 触摸设备怎么办？
- 快捷键在输入框里按 Delete 会发生什么？
- React StrictMode 下 effect 会不会重复注册事件？

**证据：**

重点看 `ImageWorkspacePage.tsx` 的快捷键、侧栏 resize、详情面板拖拽，以及 `WorkflowCanvas.tsx` 的节点事件与 `nodrag` 边界。

### Q7：为什么当前加边时要立即拒绝环路？

**推荐回答：**

执行层是 DAG，环路会让拓扑调度无法得到合法起点。如果允许非法边先进入状态，再到运行时才报错，用户会看到画布已经保存但工作流无法执行。现在 `createEdge` 复用 `validateWorkflowGraph`，在写入历史和 IndexedDB 之前拒绝自环、缺失端点、重复边和环路。

**继续拷打：**

- 静默拒绝用户能知道原因吗？
- 为什么不允许图中存在环，只在执行前检测？
- 如果以后支持循环节点怎么办？

**改进答案：**

当前 UI 还可以进一步把校验结果呈现为 toast 或边高亮；如果产品真的需要循环，应把循环作为显式的控制流节点，并在执行协议中定义最大迭代次数、退出条件和取消语义，而不是让普通数据边形成隐式环路。

## 4. 第三层：大画布、Worker 与 R-tree

### Q8：为什么需要 Worker？

**推荐回答：**

视口查询、框选和空间索引更新会随着节点数增长变成主线程计算。如果在鼠标移动、缩放时全量扫描节点，计算会和 React 更新、布局、输入事件竞争主线程。Worker 可以把纯数据计算移走，让主线程优先处理输入和可见 UI。

**继续拷打：**

- Worker 能解决 React 渲染卡顿吗？
- 数据传给 Worker 的成本怎么算？
- Worker 崩溃了怎么办？

**关键反问答案：**

Worker 不能直接解决 React 渲染本身，也不能改变算法复杂度；所以还需要视口裁剪、R-tree 和增量 patch。数据量小时，结构化克隆的成本可能抵消收益，必须用 profile 决定是否引入 Transferable。

### Q9：为什么 Worker 和 R-tree 要同时使用？

**推荐回答：**

它们优化的是两个维度：Worker 改变计算线程，R-tree 减少需要计算的对象数量。只使用 Worker，仍可能在 Worker 内遍历 10,000 个节点；只使用 R-tree，查询返回后主线程仍可能因为渲染大量节点而卡顿。当前实现用 R-tree 做范围查询，用 Worker 执行索引查询，React 只渲染可见集合。

### Q10：R-tree 的复杂度和退化场景是什么？

**推荐回答：**

范围查询平均接近 `O(log n + k)`，`k` 是命中的对象数；全量扫描是 `O(n)`。R-tree 不是任何场景都绝对更快：大视口命中大部分节点、高度重叠、索引重建或频繁更新时收益会降低。因此 benchmark 要覆盖 uniform、clustered 和 overlap 分布，比较 P50、P95、Max，并验证结果集合一致。

**继续拷打：**

- 为什么不用四叉树或网格索引？
- 你的 R-tree 更新是增量更新还是重建？
- 什么时候 Packed R-tree 不适合？

**推荐答案：**

当前是读多写少场景，更新先标记 dirty，在下一次查询时重建 Packed R-tree，避免每个指针事件都维护复杂树结构。若变成高频写、多协同光标或动态布局，可能要换支持更强增量更新的结构，或者按空间分块维护索引。

### Q11：如何避免旧的 Worker 查询结果覆盖新结果？

**推荐回答：**

主线程为每次查询分配递增的 `querySequence`，只接受当前序列的结果；Client 与 Worker 的初始化/更新请求还带版本号，更新要求 `baseVersion` 连续，查询带当前 version。视口变化时采用 latest-wins，队列中只保留最新查询，避免缩放过程中的旧结果覆盖新视图。

**继续拷打：**

- 为什么不是简单 debounce？
- 如果 Worker 响应顺序错乱怎么办？
- 如果主线程和 Worker 版本不一致怎么办？

**推荐答案：**

debounce 只能减少请求，不能解决已发请求的迟到响应；requestId、sequence 和 version 分别解决请求身份、视口新旧和数据快照一致性。发现版本缺口时要重新初始化，而不是继续在错误索引上查询。

### Q12：Worker 的三级降级怎么设计？

**推荐回答：**

优先级是：`Worker + R-tree` → `主线程 + R-tree` → `主线程 + 全量扫描`。三种模式共享 `queryVisible / boxSelect / updateNodes` 接口，故障时切换实现，不让画布整体不可用。降级必须记录诊断事件，包含模式、错误类型和耗时，不能静默降级。

**继续拷打：**

- 为什么不是 Worker 挂了就直接全量扫描？
- 降级后如何恢复 Worker？
- 降级会不会让用户误以为性能没问题？

**推荐答案：**

先保留主线程 R-tree，因为它通常还能提供较好的查询复杂度；全量扫描是最后保底。当前实现优先保证可用性，后续可在新项目或空闲时重建 Worker；同时用降级计数和长任务指标暴露风险。

### Q13：你现在的 benchmark 能证明什么，不能证明什么？

**推荐回答：**

它能证明在固定数据集和同一 Node 环境下，R-tree 与全量扫描返回结果一致，并能观察不同分布下的 P50/P95/Max 趋势。它不能证明浏览器中 React Flow 的真实 FPS、内存占用、结构化克隆成本或线上机器的用户体验，所以不能把 benchmark 结果直接说成线上性能提升。

**继续拷打：**

- 为什么不用平均值？
- 为什么测 P95 和 Max？
- 你还需要什么浏览器指标？

**推荐答案：**

平均值可能掩盖偶发长任务；P95 反映长尾交互，Max 能暴露极端卡顿。浏览器还需要 Long Task、交互延迟、可见节点数、Worker 查询耗时、降级次数和必要时的内存/帧率采样。

## 5. 第四层：AI 对话、SSE 与流式任务

### Q14：为什么用 SSE，不用 WebSocket？

**推荐回答：**

当前 Agent 的主要通信模型是服务端到前端的单向事件流，前端只需要发送一次请求并持续接收 token、状态、工具调用和完成事件，SSE 的语义更简单，浏览器调试和断线处理成本也更低。取消可以用 AbortController 加 HTTP cancel 请求完成。WebSocket 更适合多人协同画布、高频双向控制和需要服务端 ACK 的场景。

**继续拷打：**

- SSE 如何重连？
- 重连后怎么避免重复消息？
- 为什么不说 WebSocket 更实时？
- 如果一个页面有 20 个任务怎么办？

**诚实口径：**

当前项目重点实现了 SSE 消费、取消和迟到事件保护，重连补偿仍是后续工作。真正实现重连，需要服务端持久化事件序列，客户端携带 `lastSequence`，服务端补发缺口并保证幂等。

### Q15：一次 AI 请求的事件顺序是什么？

**推荐回答：**

典型链路是：`run_start → agent_status → creative_context → creative_brief → tool_call_start → tool_call_delta → tool_call_end → tool_result → text → done`。前端把文本、工具调用、状态和创作 brief 分别映射到消息 store 和 Agent 状态栏，不把模型私有思维链原样展示给用户。

**继续拷打：**

- tool call 参数为什么要增量拼接？
- tool result 到达后如何触发画布节点？
- done 到达但图片任务还没完成怎么办？

**推荐答案：**

工具参数可能分多个 delta 到达，前端按 call id 拼接；工具结果成功后解析为受约束的 `ImageOperationAction`，再创建草稿节点和生成任务。Agent 的 done 只代表对话/工具阶段完成，图片任务仍由独立任务状态跟踪，不能混为同一个成功状态。

### Q16：如何处理取消后迟到的 token、tool result 和 done？

**推荐回答：**

每次运行有独立的 `runId`，任务事件有递增 `sequence`，前端只处理当前会话、当前运行且 sequence 大于 `lastSequence` 的事件。取消时先在前端标记 cancelled 并 abort 消费，再向服务端发 cancel；取消后到达的事件全部丢弃，不能把 cancelled 改回 success。

**继续拷打：**

- AbortController 能保证服务端一定停止吗？
- 如果 cancel 请求失败呢？
- 取消和失败在 UI 上怎么区分？

**推荐答案：**

AbortController 只保证前端停止消费，服务端取消是 best effort；所以取消状态要独立建模，服务端仍要用任务状态和 Provider cancel 做最终收敛。用户主动取消显示“已取消”，网络失败显示“失败”，不能把两者混在一起。

### Q17：视觉上下文为什么要发送资产清单，而不是依赖鼠标截图？

**推荐回答：**

截图不能稳定表达资产身份、顺序和用途，模型也无法可靠知道哪张图对应哪个节点。前端发送带 `assetId、imageUrl、mimeType、尺寸、role、prompt` 的 manifest，服务端据此构造文本和 image content。下载失败的资产单独 warning，不能静默变成纯文本请求。

**继续拷打：**

- 如何防止用户引用不属于当前画布的资产？
- 为什么前端还要压缩图片？
- data URL 和远程 URL 怎么处理？

**推荐答案：**

服务端工具校验 allowedAssetIds，前端发送前展示上下文图片；视觉图片先限制最大边并转 JPEG，控制请求大小；远程 URL 和本地资源分别走 URL 或 data URL 处理，并对读取失败做可恢复降级。

## 6. 第五层：DAG 工作流执行器

### Q18：你的 DAG 执行器解决了什么问题？

**推荐回答：**

它把画布节点/边转换成可执行的依赖图：运行前校验重复节点、缺失端点、自环、重复边和环路；运行时按拓扑依赖把 ready 节点放入队列，最多并发 3 个节点；节点失败可以按最大尝试次数重试，失败分支的下游跳过，独立分支继续运行，AbortSignal 触发时传播取消。

### Q19：拓扑调度具体怎么跑？

**推荐回答：**

先构造 `dependencies` 和 `dependents`，计算每个节点的入度，把入度为 0 的节点放入 ready 队列。调度器在 active 数小于并发上限时启动节点；节点成功后更新下游依赖状态，所有依赖成功才入队；任一依赖 error、skipped 或 cancelled，则当前节点进入对应的阻塞状态。active 节点通过 `Promise.race` 回收，避免串行等待最慢任务。

**继续拷打：**

- 为什么不能简单按数组顺序执行？
- 两个节点同时依赖同一个父节点怎么处理？
- 一个节点失败时为什么不取消整条工作流？

**推荐答案：**

数组顺序不能表达并行依赖；共享父节点可以让多个 ready 节点并行；是否取消整条流程取决于产品语义，当前采用分支级失败传播，保留独立分支的结果，更适合创作工作流。

### Q20：重试会不会造成重复生成或重复写入？

**推荐回答：**

当前执行器层面只控制尝试次数和错误传播，真正接入生产 Provider 时还需要把 `taskId/runId/inputHash` 作为幂等键。重试前保留输入快照，生成结果写入时按 operationId 或 inputHash 去重，不能只靠前端按钮防重复。

**继续拷打：**

- 哪些错误应该重试？
- 参数错误重试有什么意义？
- 重试间隔怎么设计？

**推荐答案：**

网络断开、限流、临时服务不可用适合重试；参数错误、鉴权失败、模型不支持能力不应自动重试。生产环境还要加指数退避、最大总时长和 jitter，避免大量客户端同步重试。

### Q21：失败、跳过、取消、部分失败如何区分？

**推荐回答：**

- `error`：节点执行过但最终失败；
- `skipped`：节点没有执行，因为上游失败；
- `cancelled`：用户或上游取消导致节点不再执行；
- `partial_failure`：至少有成功结果，同时存在失败或被跳过分支。

这几个状态要独立展示，否则用户无法判断是模型失败、依赖失败还是主动取消。

### Q22：为什么执行器要做成纯 TS 模块？

**推荐回答：**

拓扑、入度、重试和状态传播不需要 DOM，也不应该依赖 React 生命周期。做成纯 TS 模块后可以用确定性测试覆盖环路、并发、失败和取消，也能被页面、批处理任务或后续服务端执行器复用。

## 7. 第六层：React、状态管理与浏览器基础

### Q23：为什么 Zustand，而不是 Context 或 Redux？

**推荐回答：**

工作台有项目、画布、资产、任务和聊天等跨组件状态，Context 容易让订阅边界和更新范围变得不清晰；Redux 的约束更完整，但当前个人项目需要快速拆分领域并保留较轻量的调用方式。Zustand 可以按 selector 订阅，减少组件无关更新。若团队已有 Redux Toolkit 规范，我会优先遵循团队生态，而不是坚持个人偏好。

**继续拷打：**

- Zustand selector 写错会有什么问题？
- 为什么 React Flow 实例不能放进 store？
- 哪些状态应该是组件本地状态？

**推荐答案：**

React Flow 实例、Worker、AbortController 是运行时资源，不适合持久化和序列化；输入框、弹窗、拖拽中的临时坐标属于组件本地状态；项目、节点、资产和任务属于领域状态。

### Q24：如何减少不必要的 React render？

**推荐回答：**

使用 Zustand selector 订阅必要字段，`useMemo` 转换 Flow nodes/edges，`useCallback` 固定事件回调，视口裁剪减少传给 React Flow 的节点数量，Worker 只返回可见 ID 而不是整棵对象。性能问题最终要通过 React Profiler 和 Performance 面板验证，不能只凭 memo 猜测。

### Q25：useEffect 有哪些风险？

**推荐回答：**

主要风险是重复订阅、过期闭包、依赖数组不完整和异步结果覆盖新状态。当前对窗口快捷键、项目 hydrate、Worker 生命周期和 AI 会话切换都做了清理；流式任务用 ref 保存 active run，事件回调先检查当前 run 是否仍有效。React StrictMode 下开发环境 effect 可能执行 setup-cleanup-setup，因此清理必须幂等。

### Q26：IndexedDB 持久化为什么不是每次状态变化都立即写？

**推荐回答：**

IndexedDB 是异步 IO，如果每个鼠标移动和每个 token 都写快照，会造成无意义的写放大和数据竞争。当前保存的是领域快照，运行时资源不写入；后续可以增加 debounce、版本号和写入队列，保证只提交最新快照，并在项目切换时先等待必要的持久化。

### Q27：浏览器的 Long Task 是什么？为什么要关注？

**推荐回答：**

Long Task 是主线程持续执行较长时间、阻塞输入和绘制的任务，通常用 50ms 作为重要参考阈值。画布拖拽、React 大量节点更新、图片解码和 JSON/结构化克隆都可能造成长任务。当前开发环境用 PerformanceObserver 采集 longtask 次数和总时长，同时记录 Spatial 查询 P50/P95/Max 和降级次数。

## 8. 第七层：工程化、测试与稳定性

### Q28：你做了哪些测试？为什么不只看覆盖率？

**推荐回答：**

当前有 4 组 Vitest 测试，共 11 个用例，覆盖 DAG 校验/调度、任务状态机、R-tree 与扫描基线一致性、Worker 崩溃降级和性能指标汇总。优先测状态机、空间索引、协议解析、版本连续性和 DAG 这类纯函数，因为它们是高风险边界；整体覆盖率不能替代关键链路测试。

**继续拷打：**

- 为什么没有 E2E？
- Worker 怎么测？
- 如何测试乱序事件？
- 测试会不会因为 setTimeout 不稳定？

**诚实答案：**

当前重点是稳定的纯函数和故障演练测试，完整浏览器 E2E 还可以补 Playwright，覆盖创建项目、拖拽、取消生成和刷新恢复。Worker 通过可注入的 worker factory 使用 fake Worker 演练崩溃，避免测试依赖真实浏览器线程。

### Q29：CI 门禁是什么？失败时怎么排？

**推荐回答：**

`npm run check` 依次执行服务端 typecheck、前端 typecheck、Vitest、生产构建和 canvas benchmark；GitHub Actions 在 push 和 pull request 上执行。排查顺序是先看失败阶段：类型错误看边界和依赖，单测看确定性和状态转移，构建看打包/环境，benchmark 看正确性是否回退以及 P95/Max 是否异常。

### Q30：Worker 崩溃的故障演练怎么做？

**推荐回答：**

通过注入 fake Worker，在初始化完成后让下一次查询触发 `onerror`，验证 Client 切换到 `main-r-tree`，同一个查询仍能返回正确节点集合，并且记录 `worker-error` 诊断事件。这个演练验证的是“故障可恢复 + 结果不丢 + 降级可观测”，不只是验证 console 打印了错误。

### Q31：线上出现画布突然卡顿，你怎么排查？

**推荐回答：**

先确认是所有用户还是特定项目，按项目节点数、浏览器和操作类型切分；看长任务、查询 P95/Max、可见节点数、Worker 降级次数和错误日志；用 Performance 面板确认是空间查询、React reconciliation、图片解码还是结构化克隆。若 Worker 已降级，先保障可用性并限制高成本操作，再修根因；修复后用同一 benchmark 和浏览器场景回归。

**不要说：**

“我会先加 debounce”“我会把所有东西放 Worker”“我会把 React 换成 Canvas”。这些都不是定位结论。

### Q32：如果 SSE 消息偶发重复或顺序错乱，怎么办？

**推荐回答：**

每个 run 绑定 `runId`，每个事件带 `sequence`；客户端保存最后处理的 sequence，重复和旧事件直接丢弃。若需要断线恢复，服务端要根据 lastSequence 补发缺口，客户端按事件类型做幂等更新；不能只依赖浏览器连接自动重试。

## 9. 第八层：性能与稳定性的数字拷打

### Q33：你 benchmark 的具体数据是什么？

**推荐回答模板：**

本机最近一次 `npm run benchmark:canvas` 使用 10,000 个节点、20,000 条边、300 次查询，R-tree 与全量扫描的返回集合均 PASS。当前一次结果的趋势是：uniform 的 baseline P95 约 0.39ms、R-tree 约 0.02ms；clustered 的 baseline P95 约 0.22ms、R-tree 约 0.04ms；overlap 的 baseline P95 约 0.28ms、R-tree 约 0.04ms。绝对值会随机器和运行时变化，我只把它当算法趋势和正确性基线，不当线上指标。

### Q34：为什么 benchmark 很快，用户浏览器仍然可能卡？

**推荐回答：**

benchmark 主要测空间查询，不包含 React Flow 节点渲染、边绘制、图片解码、布局、GC、设备性能和输入事件竞争。浏览器真实体验要额外看 Long Task、交互延迟、FPS/帧时间、内存和实际可见节点数，所以项目里把查询指标和 Long Task 诊断分开记录。

### Q35：你的性能优化目标是什么？

**推荐回答：**

不是单纯追求平均耗时，而是保证结果一致、交互长尾可控和故障可降级。每次优化至少回答：结果有没有变化，P95/Max 有没有回退，主线程有没有长任务，Worker 降级是否增加，内存是否可接受。

## 10. 第九层：开放性、协作与技术方案

### Q36：你如何做技术方案评审？

**推荐回答：**

先定义用户动作和可观测指标，再画状态边界和数据流；接着写协议、异常路径、取消语义、降级方案和验证方式；评审时重点让产品、算法、后端确认输入输出、错误责任和时序，不只讨论库选型。方案必须有最小可落地版本，避免一开始把所有未来能力都做进首期。

### Q37：如何平衡 AI 业务快速迭代和线上稳定性？

**推荐回答：**

把变化隔离在协议和 Provider 边界，前端用联合类型和版本号约束数据；高风险纯函数先测，外部模型调用做错误分类和取消；新能力通过 feature flag 或可降级路径上线；指标先埋好，出问题能知道是模型、网络、Worker 还是渲染层。

### Q38：算法、后端和产品意见不一致时怎么办？

**推荐回答：**

先把争议转成可验证的约束，例如延迟、成功率、成本、用户可见状态和回滚成本。对于 SSE/WebSocket 选择，先确认通信模型；对于模型结果，先确认 Provider 契约和错误责任；用小范围实验或 benchmark 代替凭感觉争论。

### Q39：你如何排查一个自己不熟的线上问题？

**推荐回答：**

先复现和缩小范围，再按链路分层：输入、状态、网络、Provider、渲染、持久化。保留最小复现、时间线和关键日志；先做止损方案，再定位根因；修复后补回归用例和监控。对于无法确认的假设明确标注，不把猜测写成结论。

### Q40：你只有 1 年正式前端经验，为什么能胜任这个岗位？

**推荐回答：**

我正式前端经验是 1 年，处在 JD 要求的下限，所以我不会把个人项目包装成多年生产经验。我的优势是已经围绕这个岗位的核心问题做过系统实践：React/TS 工作台、节点画布、流式任务、Worker/R-tree、DAG 执行和工程门禁。正式工作中的线上协作和业务结果需要用真实项目补充，但这份项目证明了我能独立拆问题、做取舍、落代码和验证。

**继续拷打：**

- 你如何证明不是只会写 Demo？
- 你遇到过最难的线上问题是什么？
- 你能接受先从具体模块做起吗？

**推荐答案：**

不能用个人项目冒充线上事故；可以用代码、测试、benchmark 和故障演练证明工程方法，再用正式工作经历证明团队协作、交付和线上责任。

## 13. 最后 5 分钟速记卡

### 画布

- React Flow 负责通用画布交互，业务节点和领域数据自己维护。
- 视口裁剪减少 React 渲染对象；R-tree 减少范围查询对象；Worker 移走纯数据计算。
- requestId/sequence/version 解决不同层级的迟到和一致性问题。
- Worker 降级：Worker + R-tree → 主线程 + R-tree → 主线程扫描。

### AI 流式

- SSE 适合当前单向 Agent 事件流，WebSocket 留给多人协同/高频双向控制。
- runId 区分运行，sequence 防重复和乱序，AbortController 停止前端消费，HTTP cancel 通知服务端。
- 工具结果不是图片完成；对话 run 和图片 generation task 分开建模。

### DAG

- 入度为 0 进入 ready 队列；active 数受 maxConcurrency 限制。
- 成功才释放下游；error/skip/cancel 传播到依赖分支。
- 重试要区分可重试错误和不可重试错误，并准备幂等键。

### 工程质量

- 11 个单测覆盖 DAG、任务状态、空间索引和 Worker 故障。
- `npm run check` = server typecheck + web typecheck + test + build + benchmark。
- 指标看 P50/P95/Max、Long Task、降级次数、可见节点数和错误类型。

### 诚实边界

- 个人项目，不冒充线上项目。
- 图片创作，不冒充视频编辑。
- 设计过 WebSocket 场景，不冒充实现过协同。
- benchmark 是趋势证据，不是线上用户指标。

## 14. 推荐的面试结束反问

1. Updream 当前节点画布更大的瓶颈是节点渲染、媒体预览，还是工作流任务调度？
2. AI 任务是前端直接消费 SSE，还是由统一任务中心通过 WebSocket/SSE 分发？
3. 团队对画布状态、任务状态和素材资产的边界有没有统一协议？
4. 这个岗位入职前三个月最希望新人独立接下哪一个核心模块？
5. 对于视频预览和时间轴，团队当前更看重快速交付还是长期编辑能力？

这些问题能把讨论引回岗位真实技术难点，也能帮助你判断项目经验和团队阶段是否匹配。
